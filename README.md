# secure-pipeline-lab

Данная лаба посвящена построению безопасного CI-пайплайна (DevSecOps) вокруг простого todo-приложения на FastAPI. Пайплайн работает на GitHub Actions: раннеры GitHub-hosted, на моем сервере ничего не крутится и оперативку не ест (self-hosted GitLab с раннером вместе с VS Code съели бы ее целиком).
Вся лаба основывается на трех принципах: не доверять ничему, что приходит снаружи (зависимости, образы, actions, код из PR); проверять как можно раньше (до коммита, а не после деплоя); эшелонированная защита - ни один сканер не дает гарантии, поэтому проверок несколько и на разных этапах.

План по этапам:
   0. Гигиена репозитория: .gitignore, закрепление зависимостей
   1. Поиск секретов: gitleaks, pre-commit хук
   2. Lint и тесты: ruff, pytest
   3. SAST: bandit, semgrep
   4. SCA: pip-audit
   5. Безопасный Dockerfile
   6. Сканирование образа и Dockerfile: trivy, hadolint
   7. SBOM
   8. DAST: OWASP ZAP baseline
   9. Подпись образа: cosign (по желанию)

## Приложение

todo-app/main.py - CRUD для задач (GET/POST /tasks, GET /tasks/{id}, PATCH /tasks/{id}/done, DELETE /tasks/{id}), задачи хранятся в памяти. Само по себе приложение ничего не запускает, это только объект app, слушает порт и принимает запросы ASGI-сервер uvicorn:
   cd todo-app
   source .venv/bin/activate
   uvicorn main:app
Документация API (Swagger) на http://127.0.0.1:8000/docs. На корень / приложение отвечает 404, обработчика для него нет.

## Этап 0. Гигиена репозитория

1. .gitignore:
   __pycache__
   *.venv
   *.env
   Шаблон без слэша срабатывает на любой глубине, поэтому правила вида todo-app/.venv и */.env заменил на эти. Проверка, какое правило сработало:
   git check-ignore -v todo-app/.env
   .venv в репозиторий не попадает: он не переносимый (см. проблему ниже) и воссоздается из requirements.txt.

2. Закрепление зависимостей:
   Изначально в requirements.txt было просто fastapi и uvicorn, без версий. При каждой установке ставилось бы то, что сейчас последнее на PyPI, вместе с возможной уязвимостью или бэкдором.
   Закрепляю через pip-tools. В requirements.in руками пишу только прямые зависимости - пакеты, а не классы (FastAPI, HTTPException, BaseModel это классы внутри пакетов fastapi и pydantic). uvicorn в коде не импортируется, но без него приложение не запустить, поэтому он тоже прямая зависимость:
   fastapi
   pydantic
   uvicorn
   requirements.txt генерирует pip-compile:
   pip install pip-tools
   pip-compile --generate-hashes
   pip install -r requirements.txt
   Из 3 прямых зависимостей получилось 14 закрепленных пакетов: остальные транзитивные (starlette приходит через fastapi, anyio через starlette и т.д.), откуда пришел пакет - видно в комментарии # via. Уязвимость может оказаться в любом из них, поэтому закреплены все.
   Хеши: версию на PyPI перезалить нельзя, но пакет могут подменить по пути (зеркало, прокси, сеть). С хешами pip проверяет, что скачанный файл именно тот, и при несовпадении установка падает. У части пакетов хешей десятки (pydantic-core) - это отдельные wheel под каждую платформу и версию Python.

Проблема по ходу: venv после переезда
   Venv изначально создавался в /home/amored/todo-app, потом папку перенес в лабу. pip list внутри показывал только pip, хотя в site-packages лежали все пакеты. Причина - в скриптах venv вшит абсолютный путь к интерпретатору (первая строка .venv/bin/pip смотрела на старое место). Venv удалил и создал заново на текущем месте.
   Вывод: venv не переносится, его не копируют и не коммитят, а пересоздают из requirements.txt.

## Этап 1. Поиск секретов

1. gitleaks через Docker:
   Ставить на сервер не стал, запускаю контейнером. Образ закреплен по digest, а не по тегу: тег можно перевесить на другой образ, digest - нет.
   docker pull zricethezav/gitleaks:v8.30.1
   (в выводе строка Digest: sha256:...)
   docker run --rm -v "$PWD:/path" zricethezav/gitleaks@sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f git /path -v
   -v "$PWD:/path" монтирует репозиторий внутрь контейнера под именем /path, поэтому и сканирую git /path. Подкоманда git сканирует всю историю коммитов, а не только текущие файлы.
   Код возврата: 0 - утечек нет, 1 - найдены. На этом держится и CI (раннер смотрит только на код возврата команды), и git-хуки.

2. Эксперимент с фейковым ключом (в локальной ветке, без push):
   Пример ключа из документации AWS (AKIAIOSFODNN7EXAMPLE) gitleaks пропускает - известные примеры в allowlist, иначе он ругался бы на каждый туториал и тест. Свой случайный ключ формата AKIA + 16 символов нашел, правило aws-access-token.
   Удалил ключ новым коммитом - gitleaks все равно его находит: секрет остается в истории. После этого ветку удалил, но и тогда коммиты остаются в .git (reflog) до git gc, git show <sha> их показывает. То же самое на GitHub после force push: из ветки коммит пропал, а по SHA какое-то время доступен.
   Вывод: если ключ уже запушен, первым делом отозвать ключ у сервиса (AWS), а уже потом чистить историю. Боты находят ключи в публичных репозиториях за минуты, а клоны и форки переписывание истории не трогает.

3. pre-commit хук:
   Проверка в CI срабатывает уже после push, а push - точка невозврата для секрета. Поэтому gitleaks запускается еще и перед каждым коммитом через pre-commit. Если gitleaks вернул 1, коммит не создается.
   pip install pre-commit
   .pre-commit-config.yaml:
   repos:
     - repo: https://github.com/gitleaks/gitleaks
       rev: 83d9cd684c87d95d656c1458ef04895a7f1cbd8e  # frozen: v8.30.1
       hooks:
         - id: gitleaks
   pre-commit install
   Ссылка по HTTPS: чужой публичный репозиторий только читается, SSH-ключ для этого не нужен, а у коллеги или на раннере его может не быть.
   rev закреплен хешом коммита, а не тегом, по той же причине, что и образ. Первый запуск долгий: pre-commit скачивает Go и собирает gitleaks, дальше окружение кешируется.
   Проверка: коммит с ключом AKIA... не создался, в git log его нет.

Принятые риски:
   Хук ставится только локально (.git/hooks не коммитится) и обходится через git commit --no-verify. Поэтому это удобство для разработчика, а обязательная проверка будет в CI.
   gitleaks ищет секреты по шаблонам, намеренно спрятанный ключ (base64, склейка из частей) он не найдет. Это страховка от случайных ошибок, а не от злоумышленника.
   В хуке вшит абсолютный путь к Python из venv (INSTALL_PYTHON в .git/hooks/pre-commit), после переезда venv хук будет искать pre-commit в PATH.
   pre-commit пока ставлю просто через pip install в venv приложения, без отдельного закрепленного requirements-dev.

Проблема по ходу: тег вместо digest
   Сначала написал образ как zricethezav/gitleaks:sha256:... - docker: invalid reference format. Через двоеточие указывается тег, digest пишется через @: zricethezav/gitleaks@sha256:...
   А еще раньше собирался подставить вместо тега хеш git-коммита релиза (40 символов) - это разные вещи: хеш коммита для git (rev в pre-commit, uses в Actions), digest sha256 (64 символа) для Docker.

Проблема по ходу: опечатка в ключе
   Первый тестовый коммит с ключом прошел хук - Passed. Оказалось, в ключе было AIKO вместо AKIA, шаблон aws-access-token не совпал. Хук работал правильно, это наглядно показало, как легко обойти поиск по шаблонам. Коммит откатил через git reset HEAD~1.

Проблема по ходу: разные версии gitleaks
   pre-commit autoupdate --freeze поставил v8.30.0, а в Docker был 8.30.1. Выровнял на 8.30.1, хеш взял через:
   git ls-remote https://github.com/gitleaks/gitleaks 'refs/tags/v8.30.*'
   v8.30.0 - аннотированный тег (две строки: объект тега и коммит ^{}), autoupdate вписал хеш объекта тега. v8.30.1 - легкий тег, одна строка, это сразу хеш коммита.
   Версия должна быть одна локально, в хуке и в CI, иначе один инструмент найдет секрет, а другой нет.

## Процесс работы

Каждый этап делаю в отдельной ветке, пушу часто, в main только через Pull Request. Push в ветку не создает новых PR, а дописывается в уже открытый. Эксперименты с секретами - только в локальных ветках, без push.
   git switch -c feature/<этап>
   git push -u origin feature/<этап>

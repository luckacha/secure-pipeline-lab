# secure-pipeline-lab

Безопасный CI-пайплайн (DevSecOps) на GitHub Actions для простого todo-приложения на FastAPI. Принципы: не доверять ничему, что приходит снаружи (зависимости, образы, actions, код из PR), ловить проблемы как можно раньше (до коммита, а не после деплоя), эшелонированная защита - ни один сканер не дает гарантии, поэтому проверок несколько.

## Кратко

Что сделано:
   - Зависимости закреплены с хешами через pip-tools: 3 прямые зависимости -> 14 закрепленных пакетов вместе с транзитивными
   - Поиск секретов gitleaks по всей истории git, образ закреплен по digest
   - pre-commit хук с gitleaks: коммит с секретом не создается, версия хука закреплена хешом коммита
   - Работа через ветки и Pull Request, в main напрямую не пушу

Ключевые выводы:
   - Все внешнее закрепляю неизменяемым идентификатором (хеш пакета, digest образа, SHA коммита), а не версией или тегом - тег можно перевесить на вредоносный код
   - Секрет, удаленный новым коммитом, остается в истории. Утекший ключ сначала отзываю, потом чищу историю
   - Хук локальный и обходится через --no-verify, поэтому обязательная проверка будет в CI
   - gitleaks ищет по шаблонам и ловит случайные утечки, а не намеренно спрятанные

Статус этапов:
   0. Гигиена репозитория, закрепление зависимостей - готово
   1. Поиск секретов: gitleaks, pre-commit - готово локально, в CI впереди
   2. Lint и тесты: ruff, pytest
   3. SAST: bandit, semgrep
   4. SCA: pip-audit
   5. Безопасный Dockerfile
   6. Сканирование образа и Dockerfile: trivy, hadolint
   7. SBOM
   8. DAST: OWASP ZAP baseline
   9. Подпись образа: cosign (по желанию)

Запуск приложения:
   cd todo-app
   python3 -m venv .venv && source .venv/bin/activate
   pip install --require-hashes -r requirements.txt
   uvicorn main:app
Swagger на http://127.0.0.1:8000/docs

## Подробный разбор

### Этап 0. Гигиена репозитория

1. .gitignore:
   __pycache__
   *.venv
   *.env
   Шаблон без слэша срабатывает на любой глубине. Проверка, какое правило сработало: git check-ignore -v <путь>.

2. Закрепление зависимостей:
   Изначально в requirements.txt было fastapi и uvicorn без версий - каждая установка тянула бы последнее с PyPI, вместе с возможной уязвимостью или бэкдором.
   В requirements.in пишу только прямые зависимости (uvicorn в коде не импортируется, но без него приложение не запустить), requirements.txt генерирует pip-compile:
   pip-compile --generate-hashes
   Закреплены и транзитивные пакеты (starlette через fastapi, anyio через starlette), откуда пришел пакет - в комментарии # via. Хеши защищают от подмены пакета по пути (зеркало, прокси, сеть): при несовпадении установка падает.

Проблема по ходу: venv после переезда
   Venv создавался в другой папке и был перенесен, после чего pip list показывал только pip. В скриптах venv вшит абсолютный путь к интерпретатору. Пересоздал на месте.
   Вывод: venv не переносится и не коммитится, его пересоздают из requirements.txt.

### Этап 1. Поиск секретов

1. gitleaks через Docker, образ закреплен по digest:
   docker run --rm -v "$PWD:/path" zricethezav/gitleaks@sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f git /path -v
   Подкоманда git сканирует всю историю, а не только текущие файлы. Код возврата 1 при находке - на этом держится и CI, и git-хуки.

2. Эксперимент с фейковым ключом (локальная ветка, без push):
   Пример ключа из документации AWS gitleaks пропускает (allowlist, иначе он ругался бы на каждый туториал), свой случайный AKIA... нашел по правилу aws-access-token.
   После удаления ключа новым коммитом gitleaks все равно его находит. После удаления ветки коммит остается в .git до git gc и доступен через git show <sha> - так же, как на GitHub после force push.
   Вывод: запушенный ключ считается скомпрометированным. Сначала отозвать его у сервиса, потом чистить историю - боты находят ключи за минуты, а клоны и форки переписывание истории не трогает.

3. pre-commit хук:
   CI срабатывает после push, а push - точка невозврата для секрета, поэтому gitleaks запускается и перед каждым коммитом.
   .pre-commit-config.yaml:
   repos:
     - repo: https://github.com/gitleaks/gitleaks
       rev: 83d9cd684c87d95d656c1458ef04895a7f1cbd8e  # frozen: v8.30.1
       hooks:
         - id: gitleaks
   pre-commit install
   Проверка: коммит с ключом не создался.
   Хеш закрепляет коммит gitleaks, а его Go-зависимости закреплены в go.sum внутри этого коммита, так что одним хешом закреплено все дерево зависимостей.

Принятые риски:
   Хук обходится через --no-verify и не ставится при git clone - обязательная проверка будет в CI.
   gitleaks не найдет намеренно спрятанный ключ (base64, склейка из частей).
   Go toolchain, который pre-commit скачивает для сборки gitleaks, в конфиге не закреплен.
   Хеш не делает код безопасным, а только фиксирует его. Обновления делаю осознанно: через отдельный PR, с просмотром changelog, без спешки после выхода релиза.
   pre-commit ставлю через pip в venv приложения, без отдельного закрепленного requirements-dev.

Проблема по ходу: тег вместо digest
   zricethezav/gitleaks:sha256:... - invalid reference format. Тег пишется через двоеточие, digest через @. И хеш git-коммита релиза (для rev в pre-commit, uses в Actions) - не то же самое, что digest образа.

Проблема по ходу: опечатка в ключе
   Первый тестовый коммит прошел хук: в ключе было AIKO вместо AKIA, шаблон не совпал. Наглядно показало, как легко обойти поиск по шаблонам.

Проблема по ходу: разные версии gitleaks
   pre-commit autoupdate --freeze поставил v8.30.0, а в Docker был 8.30.1. Хеш коммита для 8.30.1 взял через git ls-remote https://github.com/gitleaks/gitleaks 'refs/tags/v8.30.*' (у аннотированного тега хеш коммита в строке с ^{}, у легкого строка одна).
   Вывод: версия инструмента должна быть одна локально, в хуке и в CI.

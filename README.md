# secure-pipeline-lab

Безопасный CI-пайплайн (DevSecOps) на GitHub Actions для простого todo-приложения на FastAPI. Принципы: не доверять ничему, что приходит снаружи (зависимости, образы, actions, код из PR), ловить проблемы как можно раньше (до коммита, а не после деплоя), эшелонированная защита - ни один сканер не дает гарантии, поэтому проверок несколько.

## Кратко

Что сделано:
   - Зависимости закреплены с хешами через pip-tools: 3 прямые зависимости -> 14 закрепленных пакетов вместе с транзитивными
   - Поиск секретов gitleaks по всей истории git, образ закреплен по digest
   - pre-commit хук с gitleaks: коммит с секретом не создается, версия хука закреплена хешом коммита
   - GitHub Actions: gitleaks на каждый PR в main и push в main, токен только contents: read, actions закреплены по SHA, секреты в логах скрыты (--redact)
   - Ruleset на main: только через PR, merge заблокирован без зеленого gitleaks и без актуальной ветки, force push и удаление запрещены, обход правил не разрешен никому, включая меня

Ключевые выводы:
   - Все внешнее закрепляю неизменяемым идентификатором (хеш пакета, digest образа, SHA коммита), а не версией или тегом - тег можно перевесить на вредоносный код
   - Секрет, удаленный новым коммитом, остается в истории. Утекший ключ сначала отзываю, потом чищу историю
   - Хук локальный и обходится через --no-verify, поэтому обязательная проверка в CI. Проверено: коммит с --no-verify прошел хук, CI его поймал
   - CI без правил защиты ветки только сообщает о проблеме, а не запрещает merge
   - gitleaks ищет по шаблонам и ловит случайные утечки, а не намеренно спрятанные

Статус этапов:
   0. Гигиена репозитория, закрепление зависимостей - готово
   1. Поиск секретов: gitleaks, pre-commit, CI - готово
   2. Lint и тесты: ruff, pytest
   3. SAST: bandit, semgrep
   4. SCA: pip-audit
   5. Безопасный Dockerfile
   6. Сканирование образа и Dockerfile: trivy, hadolint
   7. SBOM
   8. DAST: OWASP ZAP baseline
   9. Подпись образа: cosign (по желанию)

Запуск приложения:
   cd todo-app
   python3 -m venv .venv && source .venv/bin/activate
   pip install --require-hashes -r requirements.txt
   uvicorn main:app
Swagger на http://127.0.0.1:8000/docs

## Подробный разбор

### Этап 0. Гигиена репозитория

1. .gitignore:
   __pycache__
   *.venv
   *.env
   Шаблон без слэша срабатывает на любой глубине. Venv не коммитится: в его скриптах вшит абсолютный путь к интерпретатору, он не переносится и пересоздается из requirements.txt.

2. Закрепление зависимостей:
   Изначально в requirements.txt было fastapi и uvicorn без версий - каждая установка тянула бы последнее с PyPI, вместе с возможной уязвимостью или бэкдором.
   В requirements.in пишу только прямые зависимости (uvicorn в коде не импортируется, но без него приложение не запустить), requirements.txt генерирует pip-compile:
   pip-compile --generate-hashes
   Закреплены и транзитивные пакеты (starlette через fastapi, anyio через starlette), откуда пришел пакет - в комментарии # via. Хеши защищают от подмены пакета по пути (зеркало, прокси, сеть): при несовпадении установка падает.

### Этап 1. Поиск секретов

1. gitleaks через Docker, образ закреплен по digest:
   docker run --rm -v "$PWD:/path:ro" zricethezav/gitleaks@sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f git /path -v --redact
   Подкоманда git сканирует всю историю, а не только текущие файлы. Код возврата 1 при находке - на этом держится и CI, и git-хуки.

2. Эксперимент с фейковым ключом (локальная ветка, без push):
   Пример ключа из документации AWS gitleaks пропускает (allowlist, иначе он ругался бы на каждый туториал), свой случайный AKIA... нашел по правилу aws-access-token.
   После удаления ключа новым коммитом gitleaks все равно его находит. После удаления ветки коммит остается в .git до git gc и доступен через git show <sha> - так же, как на GitHub после force push.
   Вывод: запушенный ключ считается скомпрометированным. Сначала отозвать его у сервиса, потом чистить историю - боты находят ключи за минуты, а клоны и форки переписывание истории не трогает.

3. pre-commit хук:
   CI срабатывает после push, а push - точка невозврата для секрета, поэтому gitleaks запускается и перед каждым коммитом.
   .pre-commit-config.yaml:
   repos:
     - repo: https://github.com/gitleaks/gitleaks
       rev: 83d9cd684c87d95d656c1458ef04895a7f1cbd8e  # frozen: v8.30.1
       hooks:
         - id: gitleaks
   pre-commit install
   Хеш закрепляет коммит gitleaks, а его Go-зависимости закреплены в go.sum внутри этого коммита, так что одним хешом закреплено все дерево зависимостей. Версия та же, что у образа в Docker и в CI.

4. GitHub Actions (.github/workflows/ci.yml):
   Запуск на pull_request в main и на push в main. Push в остальные ветки пайплайн не запускает, иначе на каждый push в ветку с открытым PR было бы два одинаковых запуска.
   Событие именно pull_request, а не pull_request_target: второе выполняется с секретами и токеном на запись, и checkout кода из PR в нем - известная атака (pwn request).
   permissions: contents: read - если указано хотя бы одно право, остальные становятся none. Значение по умолчанию живет в настройках репозитория, а явное в файле проходит ревью.
   runs-on: ubuntu-24.04 вместо ubuntu-latest - образ раннера делает GitHub, которому я и так доверяю, так что это ради воспроизводимости: latest однажды переедет на новую LTS.
   Шаги:
   - actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
     fetch-depth: 0 - по умолчанию скачивается только последний коммит, и gitleaks не увидел бы секрет, удаленный раньше
     persist-credentials: false - иначе checkout кладет GITHUB_TOKEN в .git/config, а эта папка дальше монтируется в чужой контейнер
   - docker run gitleaks, та же команда, что в пункте 1
     Тот же образ по digest, что и локально, вместо gitleaks-action - на один сторонний action меньше
     :ro - gitleaks только читает, писать в репозиторий ему незачем
     --redact - репозиторий публичный, логи Actions видны всем. В логе файл, строка и коммит, а вместо секрета REDACTED
   Проверка: в отдельной ветке закоммитил фейковый ключ с --no-verify, хук не запускался, в PR проверка красная, в логе REDACTED. PR закрыл без merge, ветку удалил.
   GitHub push protection этот push не остановил: в файле был только ID ключа без секретной части, рабочей пары не было.

5. Ruleset на main (Settings -> Rules -> Rulesets):
   Без него красная проверка ничего не запрещает, merge доступен.
   Require a pull request before merging
   Require status checks to pass: gitleaks, плюс ветка должна быть актуальной относительно main - два PR могут быть зелеными по отдельности и сломаться вместе
   Block force pushes, запрет удаления ветки
   Bypass list пустой - правила действуют и на владельца

Принятые риски:
   gitleaks не найдет намеренно спрятанный ключ (base64, склейка из частей).
   Go toolchain, который pre-commit скачивает для сборки gitleaks, в конфиге не закреплен.
   Хеш не делает код безопасным, а только фиксирует его. Обновления делаю осознанно: через отдельный PR, с просмотром changelog, без спешки после выхода релиза.
   pre-commit ставлю через pip в venv приложения, без отдельного закрепленного requirements-dev.

## Ошибки и выводы

   - В uses сначала стоял не тот владелец (aiqiaoy/checkout вместо actions/checkout), хотя SHA был от официального v7.0.1. Проверять в uses не только версию, но и владельца - это тот же typosquatting, что и у пакетов.
   - Включил в ruleset Require status checks, но не выбрал ни одной проверки - merge красного PR оставался доступен. Проверять, что правило действительно что-то требует, а не только что галочка стоит.
   - Тестовый ключ с опечаткой (AIKO вместо AKIA) прошел хук без единого предупреждения. Поиск по шаблонам обходится одной буквой.
   - pre-commit autoupdate поставил другую версию gitleaks, чем в Docker. Версия инструмента должна быть одна локально, в хуке и в CI, иначе один найдет секрет, а другой нет.

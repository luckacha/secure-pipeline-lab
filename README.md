# secure-pipeline-lab

Безопасный CI-пайплайн (DevSecOps) на GitHub Actions для простого todo-приложения на FastAPI. Принципы: не доверять ничему, что приходит снаружи (зависимости, образы, actions, код из PR), ловить проблемы как можно раньше (до коммита, а не после деплоя), эшелонированная защита - ни один сканер не дает гарантии, поэтому проверок несколько.

## Кратко

Что сделано:
   - Зависимости закреплены с хешами через pip-tools: 3 прямые зависимости -> 14 закрепленных пакетов вместе с транзитивными
   - Поиск секретов gitleaks по всей истории git, образ закреплен по digest
   - pre-commit хук с gitleaks: коммит с секретом не создается, версия хука закреплена хешом коммита
   - GitHub Actions: gitleaks на каждый PR в main и push в main, токен только contents: read, actions закреплены по SHA, секреты в логах скрыты (--redact)
   - Ruff проверяет Python-код и форматирование, pytest запускает 6 тестов API с очисткой состояния перед каждым тестом
   - GitHub Actions: отдельная job lint-tests устанавливает зависимости с хешами и запускает Ruff и pytest на Python 3.13
   - SAST в той же job: Bandit проверяет Python-код, Semgrep запускает локальное правило запрета eval; оба проверяют todo-app/main.py
   - Ruleset на main: только через PR, merge заблокирован без зеленых gitleaks и lint-tests и без актуальной ветки, force push и удаление запрещены, обход правил не разрешен никому, включая меня

Ключевые выводы:
   - Все внешнее закрепляю неизменяемым идентификатором (хеш пакета, digest образа, SHA коммита), а не версией или тегом - тег можно перевесить на вредоносный код
   - Секрет, удаленный новым коммитом, остается в истории. Утекший ключ сначала отзываю, потом чищу историю
   - Хук локальный и обходится через --no-verify, поэтому обязательная проверка в CI. Проверено: коммит с --no-verify прошел хук, CI его поймал
   - CI без правил защиты ветки только сообщает о проблеме, а не запрещает merge
   - Зеленые тесты проверил поломкой: изменение done на False обнаружил pytest, а неверный ожидаемый статус в отдельном PR сделал lint-tests красным и заблокировал merge
   - gitleaks ищет по шаблонам и ловит случайные утечки, а не намеренно спрятанные
   - SAST обнаруживает опасную конструкцию, даже если тесты ее не вызывают. Обнаружение проверил намеренными находками, блокировку merge - отдельными PR для Bandit и Semgrep

Статус этапов:
   0. Гигиена репозитория, закрепление зависимостей - готово
   1. Поиск секретов: gitleaks, pre-commit, CI - готово
   2. Lint и тесты: ruff, pytest, обязательная проверка в CI - готово
   3. SAST: bandit, semgrep с одним локальным правилом - готово
   4. SCA: pip-audit
   5. Безопасный Dockerfile
   6. Сканирование образа и Dockerfile: trivy, hadolint
   7. SBOM
   8. DAST: OWASP ZAP baseline
   9. Подпись образа: cosign (по желанию)

Запуск приложения:
   cd todo-app
   python3 -m venv .venv && source .venv/bin/activate
   pip install --require-hashes -r requirements.txt
   uvicorn main:app
Swagger на http://127.0.0.1:8000/docs

Проверки из папки todo-app с активированным venv:

   python -m pip install --require-hashes -r requirements-dev.txt
   python -m ruff check .
   python -m ruff format --check .
   python -m pytest -v
   python -m bandit main.py

Semgrep из корня репозитория, Docker-образ закреплен по digest:

   docker run --rm -v "$PWD:/src:ro" semgrep/semgrep@sha256:451b3d875c00dac7ed5db5293e584a07de11449a409c10b3c2d2652f429630b6 semgrep scan --config /src/semgrep/python.yml --metrics=off --disable-version-check --error /src/todo-app/main.py

## Подробный разбор

### Этап 0. Гигиена репозитория

1. .gitignore:
   __pycache__
   *.venv
   *.env
   Шаблон без слэша срабатывает на любой глубине. Venv не коммитится: в его скриптах вшит абсолютный путь к интерпретатору, он не переносится и пересоздается из requirements.txt.

2. Закрепление зависимостей:
   Изначально в requirements.txt было fastapi и uvicorn без версий - каждая установка тянула бы последнее с PyPI, вместе с возможной уязвимостью или бэкдором.
   В requirements.in пишу только прямые зависимости (uvicorn в коде не импортируется, но без него приложение не запустить), requirements.txt генерирует pip-compile:
   pip-compile --generate-hashes
   Закреплены и транзитивные пакеты (starlette через fastapi, anyio через starlette), откуда пришел пакет - в комментарии # via. Хеши защищают от подмены пакета по пути (зеркало, прокси, сеть): при несовпадении установка падает.

### Этап 1. Поиск секретов

1. gitleaks через Docker, образ закреплен по digest:
   docker run --rm -v "$PWD:/path:ro" zricethezav/gitleaks@sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f git /path -v --redact
   Подкоманда git сканирует всю историю, а не только текущие файлы. Код возврата 1 при находке - на этом держится и CI, и git-хуки.

2. Эксперимент с фейковым ключом (локальная ветка, без push):
   Пример ключа из документации AWS gitleaks пропускает (allowlist, иначе он ругался бы на каждый туториал), свой случайный AKIA... нашел по правилу aws-access-token.
   После удаления ключа новым коммитом gitleaks все равно его находит. После удаления ветки коммит остается в .git до git gc и доступен через git show <sha> - так же, как на GitHub после force push.
   Вывод: запушенный ключ считается скомпрометированным. Сначала отозвать его у сервиса, потом чистить историю - боты находят ключи за минуты, а клоны и форки переписывание истории не трогает.

3. pre-commit хук:
   CI срабатывает после push, а push - точка невозврата для секрета, поэтому gitleaks запускается и перед каждым коммитом.
   .pre-commit-config.yaml:
   repos:
     - repo: https://github.com/gitleaks/gitleaks
       rev: 83d9cd684c87d95d656c1458ef04895a7f1cbd8e  # frozen: v8.30.1
       hooks:
         - id: gitleaks
   pre-commit install
   Хеш закрепляет коммит gitleaks, а его Go-зависимости закреплены в go.sum внутри этого коммита, так что одним хешом закреплено все дерево зависимостей. Версия та же, что у образа в Docker и в CI.

4. GitHub Actions (.github/workflows/ci.yml):
   Запуск на pull_request в main и на push в main. Push в остальные ветки пайплайн не запускает, иначе на каждый push в ветку с открытым PR было бы два одинаковых запуска.
   Событие именно pull_request, а не pull_request_target: второе выполняется с секретами и токеном на запись, и checkout кода из PR в нем - известная атака (pwn request).
   permissions: contents: read - если указано хотя бы одно право, остальные становятся none. Значение по умолчанию живет в настройках репозитория, а явное в файле проходит ревью.
   runs-on: ubuntu-24.04 вместо ubuntu-latest - образ раннера делает GitHub, которому я и так доверяю, так что это ради воспроизводимости: latest однажды переедет на новую LTS.
   Шаги:
   - actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
     fetch-depth: 0 - по умолчанию скачивается только последний коммит, и gitleaks не увидел бы секрет, удаленный раньше
     persist-credentials: false - иначе checkout кладет GITHUB_TOKEN в .git/config, а эта папка дальше монтируется в чужой контейнер
   - docker run gitleaks, та же команда, что в пункте 1
     Тот же образ по digest, что и локально, вместо gitleaks-action - на один сторонний action меньше
     :ro - gitleaks только читает, писать в репозиторий ему незачем
     --redact - репозиторий публичный, логи Actions видны всем. В логе файл, строка и коммит, а вместо секрета REDACTED
   Проверка: в отдельной ветке закоммитил фейковый ключ с --no-verify, хук не запускался, в PR проверка красная, в логе REDACTED. PR закрыл без merge, ветку удалил.
   GitHub push protection этот push не остановил: в файле был только ID ключа без секретной части, рабочей пары не было.

5. Ruleset на main (Settings -> Rules -> Rulesets):
   Без него красная проверка ничего не запрещает, merge доступен.
   Require a pull request before merging
   Require status checks to pass: gitleaks; на этапе 2 добавил lint-tests. Ветка должна быть актуальной относительно main - два PR могут быть зелеными по отдельности и сломаться вместе
   Block force pushes, запрет удаления ветки
   Bypass list пустой - правила действуют и на владельца

Принятые риски:
   gitleaks не найдет намеренно спрятанный ключ (base64, склейка из частей).
   Go toolchain, который pre-commit скачивает для сборки gitleaks, в конфиге не закреплен.
   Хеш не делает код безопасным, а только фиксирует его. Обновления делаю осознанно: через отдельный PR, с просмотром changelog, без спешки после выхода релиза.
   pre-commit ставлю через pip в venv приложения; сам пакет pre-commit не включен в закрепленные dev-зависимости.

### Этап 2. Lint и тесты

1. Зависимости для разработки:
   В todo-app/requirements-dev.in добавил ruff, pytest и httpx2 для TestClient. Через -r requirements.in подключаю зависимости приложения, через -c requirements.txt ограничиваю их версии уже закрепленными - локальные тесты и CI используют те же версии, что и приложение.

   pip-compile --generate-hashes requirements-dev.in
   python -m pip install --require-hashes -r requirements-dev.txt

   requirements-dev.txt храню в git. В CI устанавливаю готовый файл с проверкой хешей, а не разрешаю зависимости заново при каждом запуске.

2. Ruff:
   python -m ruff check .
   python -m ruff format --check .

   Первая команда ищет нарушения включенных правил Python-кода, вторая проверяет форматирование. В CI не использую --fix и не форматирую файлы автоматически: нарушение должно остановить проверку, а исправление пройти через PR.

3. Тесты API в todo-app/tests/test_tasks.py:
   Через FastAPI TestClient отправляю запросы приложению без отдельного запуска uvicorn. Проверяю HTTP-статусы и содержимое ответов через assert.
   Написал 6 тестов: пустой список; создание задачи и появление в списке; 404 для отсутствующей задачи; 422 при создании без title и отсутствие новой задачи; отметка выполнения с повторным GET; удаление с последующим 404 и пустым списком.
   Задачи хранятся в общем словаре main.tasks. Фикстура reset_tasks с autouse=True перед каждым тестом очищает словарь и сбрасывает main.next_id в 1, чтобы результат не зависел от порядка запуска.

   python -m pytest -v

   Результат рабочего варианта - 6 passed. Временно заменил task.done = True на False: тест выполнения упал. Вернул True - все тесты снова прошли. Так проверил, что тест замечает сломанное поведение.

4. Job lint-tests в GitHub Actions:
   Отдельная от gitleaks job на ubuntu-24.04. Checkout закреплен тем же SHA, persist-credentials: false. actions/setup-python закрепил SHA 6d4fd22b20465ccc0f7354476588e8df7c9ca0e0, Python выбрал 3.13.
   defaults.run.working-directory: todo-app - команды выполняются относительно репозитория на runner, а не по пути моего сервера.
   Установка зависимостей, ruff check, ruff format --check и pytest вынесены в отдельные шаги. По логу видно, какой шаг упал. Рабочий PR прошел обе job и был слит в main.

5. Обязательная проверка перед merge:
   В ruleset на main добавил lint-tests рядом с gitleaks.
   Проверил отдельным PR: в тесте пустого списка поменял ожидаемый статус с 200 на 201. lint-tests стал красным, GitHub заблокировал merge. PR закрыл без слияния, экспериментальную ветку удалил на GitHub.

Принятые риски:
   6 тестов покрывают основные сценарии, а не все возможные входные данные и ошибки. Зеленый pytest не доказывает отсутствие уязвимостей; SAST дополняет тесты на этапе 3, проверка зависимостей и DAST остаются впереди.
   TestClient вызывает приложение внутри процесса - сеть и запуск через uvicorn этими тестами не проверяются.
   Python закреплен до 3.13, но patch-версия может меняться. ubuntu-24.04 тоже получает обновления; окружение не зафиксировано побитово.

### Этап 3. SAST

1. Bandit:
   Добавил bandit в requirements-dev.in, пересобрал requirements-dev.txt через pip-compile --generate-hashes. Версия 1.9.4 и транзитивные зависимости закреплены с хешами.

   python -m bandit main.py

   На рабочем приложении находок нет. Временный bandit_demo.py с вводом строки и subprocess.run(command, shell=True) дал B404 на импорт subprocess и B602 на вызов с shell=True. Код завершения - 1. Сам файл не запускал, после эксперимента удалил.
   Импорт subprocess сам по себе не доказывает уязвимость. При shell=True оболочка интерпретирует строку, и пользовательский ввод может стать командой. Для фиксированной программы передача аргументов списком без оболочки убирает интерпретацию shell, но допустимые операции и аргументы все равно нужно ограничивать.
   Severity показывает оценку серьезности находки, confidence - уверенность анализатора в ее обнаружении. Это повод проверить контекст, а не доказательство эксплуатации.

2. Проверка Bandit в CI:
   После pytest добавил шаг python -m bandit main.py в обязательную job lint-tests.
   В отдельном PR добавил невызванную функцию с eval(expression). Ruff и тесты прошли, Bandit нашел B307, Medium / High, и завершился с кодом 1. Merge был заблокирован. PR закрыл без слияния, экспериментальную ветку удалил на GitHub.

3. Semgrep и локальное правило:
   Образ semgrep/semgrep закрепил по digest sha256:451b3d875c00dac7ed5db5293e584a07de11449a409c10b3c2d2652f429630b6. Тот же образ использую локально и в CI; репозиторий монтирую только для чтения через :ro.
   В semgrep/python.yml храню одно учебное правило python-no-eval для Python: pattern: eval(...), severity: ERROR. Оно ищет вызов eval с любыми аргументами. Правило проходит ревью вместе с кодом и не скачивается из изменяемого удаленного набора при каждом запуске.
   Команда запуска приведена в разделе «Кратко». --config указывает локальный YAML, --metrics=off отключает метрики, --disable-version-check отключает проверку версии, --error дает код 1 при находке.
   На main.py получил 0 находок и код 0. Временно добавил функцию с eval: правило нашло вызов и вернуло 1. Функцию удалил перед переносом рабочего варианта в CI.

4. Semgrep в CI и проверка блокировки:
   Шаг semgrep идет после Bandit в job lint-tests. Для него working-directory: . переопределяет общий каталог todo-app - контейнеру нужны и приложение, и папка semgrep из корня репозитория.
   Рабочий вариант прошел CI и был слит в main. Затем в отдельном PR временно заменил шаблон eval(...) на FastAPI(...), оставив приложение без изменений. Это намеренно неверная политика для проверки механизма, а не уязвимость FastAPI.
   Предыдущие шаги прошли, Semgrep нашел существующий вызов FastAPI и завершился с кодом 1. Merge был заблокирован. PR закрыл без слияния, ветку удалил, в main осталось правило eval(...).

Принятые риски:
   Semgrep проверяет только одно локальное правило запрета eval. Это демонстрация собственной политики, а не полноценное покрытие Python или FastAPI готовыми наборами правил. Частично дублирует B307 в Bandit.
   Оба анализатора сканируют только main.py. При появлении новых модулей область проверки нужно расширить; зависимости, контейнер и работающее приложение этими командами не проверяются.
   Находка может оказаться ложным срабатыванием, а отсутствие находок не гарантирует безопасность. Логику приложения и допустимость входных данных нужно разбирать отдельно.
   Правила Semgrep лежат в том же репозитории и могут быть ослаблены изменением в PR. Проверка обязательна, но корректность самой политики требует ревью.

## Ошибки и выводы

   - В uses сначала стоял не тот владелец (aiqiaoy/checkout вместо actions/checkout), хотя SHA был от официального v7.0.1. Проверять в uses не только версию, но и владельца - это тот же typosquatting, что и у пакетов.
   - Включил в ruleset Require status checks, но не выбрал ни одной проверки - merge красного PR оставался доступен. Проверять, что правило действительно что-то требует, а не только что галочка стоит.
   - Тестовый ключ с опечаткой (AIKO вместо AKIA) прошел хук без единого предупреждения. Поиск по шаблонам обходится одной буквой.
   - pre-commit autoupdate поставил другую версию gitleaks, чем в Docker. Версия инструмента должна быть одна локально, в хуке и в CI, иначе один найдет секрет, а другой нет.
   - Зеленый CI проверил намеренной поломкой: тест должен падать при нарушении поведения, а обязательная проверка - запрещать merge. Это две отдельные проверки, обе подтвердил экспериментом.
